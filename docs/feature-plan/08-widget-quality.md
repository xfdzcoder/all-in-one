# 08 · 组件与接入质量规范（指标设计 · 完成定义）

> **Q40b 产出**（2026-10-01，**D47**）。来源：用户批评四服务指标"没有从用户角度考虑……完全是作为一个 demo 来做的"，并要求建立自我约束。本规范是**硬约束**：凡新增组件、接入第三方服务、或改动卡片指标，必须走完 §2 推导顺序并满足 §5 完成定义（DoD）。DoD 同步进 [AGENTS.md](../../AGENTS.md)，流程载体为项目 skill `.opencode/skills/service-integration/`。
>
> 配套调研证据库：[research/00-service-metrics.md](research/00-service-metrics.md)（同类产品对照 + 真机实测可用性）。

## 1. 适用范围与核心原则

- 适用：`apps/web` 组件卡片、`apps/server` connector/适配器、`packages/widget-sdk` 契约中涉及"向用户展示数据"的一切改动。
- **核心原则：先写用户问题，再定指标，再选 API。** 推导方向永远是「用户想回答什么 → 去 API 找答案」，绝不允许「API 给什么 → 就展示什么」。
- 项目定位：**生产使用的个人工作台**，不是 demo。卡片要经得起每天看。

## 2. 推导顺序（每张数据卡片/每次接入必须逐步产出，留痕在当轮记录或 research/）

1. **用户问题清单**：persona = 自托管/家庭服务器拥有者，打开卡片 5 秒内想回答的问题，3–5 条。例：Portainer 卡 = "我的容器都活着吗？哪些炸了？"。
2. **对照物**：该服务官方 UI + 至少一个成熟 dashboard（Homarr / Homepage / Grafana 等）对同一服务展示什么。结论留痕。
3. **指标映射表**：`用户问题 → 指标 → 数据来源（接口）→ 取不到时的降级`，四列缺一不可。
4. **API 落实**：多接口聚合补齐指标；多版本路由回落（如 Immich `/api/server/statistics` ↔ 旧版 `/api/statistics`）；**理解目标服务的权限模型**（细粒度 API Key、token scope）。
5. **真机验证**：见 §4。

## 3. 展示形态（**D48**：结构化卡片 + 迷你图表）

- 卡片结构分层：**主指标**（1 个，最大字号）/ **次指标**（2–4 个）/ **状态徽标**（健康·异常·进行中）/ **清单**（异常条目、最近条目、正在发生）/ **迷你趋势**（速率类，客户端累积轮询序列）。
- 数字必须带单位与语义（`95.2 GB`、`23/25 运行中`、`2 天前` 相对时间+悬浮绝对）。
- 异常优先：有异常清单就置顶高亮；全健康给绿态一句话，不留空。

## 4. 真机验证纪律

- **拿得到真实实例的接入，必须连真机看过卡片才算完成**；否则只能标注"待真机验证"，不得在 07 勾 `[x]`。
- 真机凭证只落 `.opencode/.env.verify`（`.env.*` 已 gitignore）：**不入库、不入日志、不进前端**；用后提醒用户轮换。
- 真机验证至少覆盖：主指标数值与官方 UI 对得上、每条降级路径的文案真实、无整卡空白。

## 5. 完成定义（DoD）——勾全才算完成

- [ ] 用户问题清单已写（3–5 条）并逐条有对应指标
- [ ] 对照物已查（官方 UI + 成熟 dashboard），结论留痕
- [ ] 指标映射表四列齐全（含降级列）
- [ ] 降级文案是"原因 + 怎么修"，**没有任何"该服务未提供 X"式的甩锅文案**（除非确证服务真没有，且引用证据）
- [ ] 多接口聚合 / 多版本回落已实现，单接口失败不整卡空白
- [ ] 契约测试覆盖归一逻辑（含各降级分支）
- [ ] 真机验证通过（或显式标注"待真机验证"+ 已列入待办）
- [ ] 单位/相对时间/异常高亮符合 §3
- [ ] `pnpm test` / `typecheck` / `lint` 全绿，UI 行为有 verify 断言

## 6. 反模式清单（历史教训，禁止再犯）
