## 3 · 分级标准

| 级别 | 判据 |
|---|---|
| **P0** | 崩溃/白屏不可恢复、数据丢失、安全漏洞（越权/注入/SSRF 绕过/凭证泄漏）、契约破坏、错误的持久化写入 |
| **P1** | 功能缺陷、静默失败/错误处理缺失、潜在逻辑错误、易回归且无守卫的测试盲区、内存/性能隐患、D47 降级违规 |
| **P2** | 重复代码、命名/文案/风格不一致、文档瑕疵与过时注释、可维护性（超大文件/深嵌套/魔法数）、死代码 |

## 4 · 条目格式（每条必填）

`| ID | 位置 | 问题 | 级别 | 建议修法 |`

- ID 前缀：`SRV-`（10）/ `WEB-`（11）/ `SDK-`/`CON-`（12）/ `TST-`（13）/ `DEP-`/`SEC-`/`LNT-`（14）/ `DOC-`（15），编号递增。
- **位置**必须精确到 `文件:行`；同类问题可合并为一条并列出全部位置。
- **证据优先**：实测命令输出 / 具体代码行为；不许「可能有问题」式猜测——拿不准就写进报告末尾的「存疑（不入台账）」小节。
- 每份报告末尾给出：本区条目统计（P0/P1/P2 各几条）。

## 5 · 硬约束（评估子代理）

1. **只读评估**：不改产品代码、不改其它文档（只写自己的报告文件）、不 commit、不 push、不装包。
2. 报告**不得出现任何凭证/密钥/token 明文**（`.opencode/.env.verify` 之类只许提文件名与键名）。
3. 不评 ⑭⑮（已入台账）；不写修复代码（只给「建议修法」）。
4. 不扩大范围：非目标（Kanban/邮件/监控之外的扩展、多用户/公网）不在体检范围。
